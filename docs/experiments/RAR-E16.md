## Part 1

**A.3.2 consolidation release gate - REGISTERED, NOT YET RUN.** Candidate: the A.3.1 head (`dev` after the toolchain bump), PGO pext, hash in the manifest. Baseline: the 2.3.2 release binary `rarog-v2.3.2-windows-pext-native-pgo.exe`. `tools/sprt.ps1`, `3+0.03`, 1T, Hash 64, paired UHO, no adjudication, **`[3,10]` nElo**, cap 16,000 games; then `-Mode fixed -Games 400` at `10+0.1` 1T and at `10+0.1` 4T (no affinity, after a 4T null pair), zero forfeits required. **SCOPE CORRECTION, maintainer decision 2026-09-09, before any gate game.** `3+0.03` is the gate's clock at **both** 1T and 4T: the SPRT above plus a `3+0.03` 4T direction check. `10+0.1` moves out of the gate to a pre-release check, run before publishing or when something specific calls for it, rather than as a condition of the verdict. **The 4T null pair is dropped**, not deferred: the maintainer records the harness's multi-thread configuration as already calibrated and trusted, so re-establishing it is not a cost this gate pays. The note below about the null being unsized is retained as the reason it was raised and is no longer an obstacle to this gate; it still applies to RAR-M46, which registers its own 4T null. Bracket chosen because the prior is genuinely large: the 2026-09-04 pool measured the head's predecessor at +43.7 Elo head-to-head over 2.3.2 in 400 games, and RAR-M10 sizes `[3,10]` at a few thousand games for a true +30. **BASELINE CORRECTION, 2026-09-09, before any gate game — the registered baseline artifact was wrong and is replaced.** The row named `rarog-v2.3.2-windows-pext-native-pgo.exe` as "the 2.3.2 release binary". It is neither. (i) The file sitting at that path benches **7,601,220 / EBF 2.474** — the *development head's* fingerprint — and reports `id name Rarog 2.3.2` only because `dev`'s `Cargo.toml` version has not been bumped since the release; it is a dev build made on 2026-09-09 at 12:29, not a 2.3.2 build. Running the gate as registered would have measured the head against itself and returned H0, which the row's own note would then have read as six accepted gates collapsing at once. (ii) `--native` is never released: `build.yml` ships `--arch {x86-64, avx2, pext, arm64}`, and both `xtask` and `build_test.ps1` document native as local-only. (iii) The pairing could not have run anyway — `sprt.ps1`'s build-flavor guard hard-fails `pext-pgo` against `pext-native-pgo`. **Replacement baseline, built from the release recipe:** `tools/test_engines/rarog-e16base232-pext-pgo.exe`, `cargo xtask build --arch pext --pgo` from tag `v2.3.2` (`f931722`) in a throwaway worktree via `build_test.ps1 -SourceRoot`, manifest `git_dirty: false`, SHA-256 `069E419E...C846B1DF`, **bench 6,519,711 / EBF 2.449 — byte-equal to the fingerprint RAR-M12 independently recorded for the 2.3.2 baseline**, which is what establishes the identity. Built with `RUSTUP_TOOLCHAIN=1.98.1` rather than 2.3.2's own 1.97.1 pin, because `sprt.ps1`'s compiler-equality guard hard-fails a mixed-compiler pair and RAR-P18 measured the two compilers as indistinguishable (-0.53%, CI straddling zero); the arms therefore differ in engine source only. Its hash differs from RAR-M12's `389E234E...` asset for that reason plus PGO profile luck. **Candidate:** `tools/test_engines/rarog-e16cand-pext-pgo.exe`, `dev`, `git_dirty: false`, SHA-256 `889B3179...F1856083`, bench 7,601,220 / EBF 2.474. Both arms `verify-isa --arch pext` clean, both 9 UCI options. **Live-wire check, 4 games, decides nothing and is not evidence:** flavor equality OK, compiler equality OK, adjudication none, UHO book indexed, affinity across 14 physical cores, concurrency 14, natural termination, zero crashes or timeouts. **Nothing else changed:** bounds `[3,10]`, cap 16,000, `3+0.03`, 1T, Hash 64, paired UHO, no adjudication, and the prediction below are exactly as registered. **One registered step is unsized and cannot be started as written: the 4T null pair.** The row requires one before the 4T direction check but fixes neither its game count nor its clock, and `sprt.ps1 -Mode calibrate` bounds a null in **nElo**, not Elo. Scaling RAR-E15's 1,950 games at +/-15.42 nElo, a +/-10 nElo null needs roughly **4,600 games**; at `10+0.1` with the 4T concurrency of 3 that is on the order of **17 hours**, against about **1 to 1.5 hours** for the same null at `3+0.03` and concurrency 3. A 4-game parse check confirmed the mechanics — affinity correctly dropped for `Threads>1`, concurrency auto-resolved to 3, and the tolerance check correctly refused an interval it could not establish. **RESOLVED by the scope correction above:** the maintainer dropped the 4T null for this gate as already-calibrated harness behaviour, so nothing here blocks RAR-E16. **RAR-M46 carries the same defect** — it registers a 4T null of "400 games, inside +/-10 Elo", which neither the unit nor the game count can deliver — and should be resized before A.8.2 runs.

## Part 3

**Calibration, appended after exposure; the prediction is not rewritten.** Sign, mechanism and both direction checks were right; the two misses are **magnitude** and **speed**. Predicted +30 to +50 STC, measured **+54.77**, just above the band's top with a CI of [+37.7, +71.8] that overlaps it heavily. Predicted H1 within 5,000 games, reached at **742** — under a sixth of that, which is the same RAR-M10 relationship RAR-E15 validated, working in the other direction: a large true effect resolves fast. **The failed assumption is identifiable and is about additivity.** The band was built by summing the accepted rows since 2.3.2 (+15.6, +2.3, +22.0, +6.7, +11.8, +12.1 = +70.5 nominal) and discounting hard for non-additivity. The measurement says that discount was too aggressive — but **not by as much as the point estimate suggests**, because an SPRT that stops at a boundary reports an effect biased upward, and this one stopped at 4.6% of its cap. **Do not quote +54.77 as the head's Elo over 2.3.2.** RAR-E15's row makes the same point about its own +12.12 +/- 10.17: an SPRT decides, it does not estimate. The honest reading is "clearly and substantially positive, magnitude not settled", and the release rule is satisfied on the number the rule is written on. **The 4T number is not evidence that the head scales better.** It is a fixed-size run, so it carries no stopping bias, but 1T and 4T are different populations with different draw rates (40.70% against 34.00%) and are not comparable as Elo. It was registered as a direction check and it is reported as one. **The 4T run's zero forfeits are NOT evidence for A.3.3's host-saturation hypothesis, and must not be cited as such.** At the 1T rate of 0.135%, 400 games expect 0.54 forfeits and P(zero) is about 0.58, so a clean 400-game run is the unsurprising outcome whether or not concurrency 3 helps. A.3.3 needs its registered 10,000-game run to say anything here.
