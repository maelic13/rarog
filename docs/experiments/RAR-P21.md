# RAR-P21 — A.4.1 `cc` 1.3.0 -> 1.4.5 and the Fathom build contract, COMPLETE 2026-09-10 (`1bf8171`)

Indexed under *6. Throughput, build and platforms* in [`docs/EXPERIMENTS.md`](../EXPERIMENTS.md).

## Experiment and conditions

**A.4.1 `cc` 1.3.0 -> 1.4.5 and the Fathom build contract, COMPLETE 2026-09-10 (`1bf8171`).** `cc` compiles `vendor/fathom/src/tbprobe.c`, and `build.rs` hands it a tier-dependent `TB_NO_HW_POP_COUNT` derived from `CARGO_CFG_TARGET_FEATURE`; mis-handling that define is how the 2.3.0 and 2.3.1 baseline assets shipped **15 illegal `popcntq`**, so a `cc` bump is a build-contract change and not a version number. Manifest floor raised `cc = "1.3"` -> `"1.4"` so it tracks what has been verified rather than what merely resolves; `find-msvc-tools` follows 0.1.9 -> 0.1.12. The bump also exposed an **A.3.1 oversight**: `Cargo.toml` asserted in a comment that MSRV is kept in lockstep with `rust-toolchain.toml`, but the toolchain moved to 1.98.1 while `rust-version` stayed at `1.97` - visible because cargo reported "Locking 2 packages to latest Rust 1.97 compatible versions". Corrected to `1.98`; it changed nothing here (1.4.5 is latest under either floor) but the asserted invariant was false. Hosts: 5950X Windows x86-64 and the MacBook Air M4, both on `rustc 1.98.1`.

## Result / disposition

**GREEN on every checked surface, and one prior claim of mine is corrected below.** `verify-isa` holds on `base`, `avx2`, `pext` and `pext --pgo` on Windows x86-64 and on `arm64 --pgo` on macOS; **base is `popcnt 0`, `bmi2 0`**, so the 2.3.0-era defect has not returned. Bench fingerprint **7,601,220 / EBF 2.474** on all three x86 tiers. PGO builds, profile merges. Tests: debug **283** passed, release **284**, **0 failed**, 26/26 targets `ok` in each; the single release-only test is `#[cfg(not(debug_assertions))]` by construction; `xtask` and `texel-tuner` 15 passed. `cargo fmt --check` clean; `cargo clippy --workspace --all-targets --all-features -- -D warnings` **zero**. **The macOS question is answered, and the answer is not the one the question assumed.** `cc` 1.4.5 does **not** close the gap - the M4 still prints `Inherited flag "-fprofile-use=..." is not supported by the currently used CC` - so it is not a `cc` defect. Chasing it further produced the real finding: **no platform compiles Fathom with PGO.** The Windows C invocation, captured in full, is `cl.exe -nologo -MD -O2 -Brepro -I vendor/fathom/src -W0 /TP /std:c++17 -DTB_NO_HELPER_API -Fo... -c tbprobe.c` - **no profile flag of any form**. macOS is simply the only platform that says so out loud, because there the compiler is clang-like, `cc` tries to translate `-C profile-use` into `-fprofile-use`, and the support probe rejects it; MSVC has no LLVM-profile equivalent at all, so the flag is dropped without comment. (The same command also confirms the tier logic: `TB_NO_HW_POP_COUNT` is correctly **absent** on `pext`, whose baseline includes POPCNT.)

## Conditional lesson and retry trigger

**CORRECTION to an earlier claim in this project's own notes, recorded rather than quietly fixed.** RAR-P19 and the first draft of PLAN A.4.1 said Windows "shows no such warning", with the implication that the C half is profiled there and macOS is the outlier. That was wrong, and it was wrong in the standard way: *absence of a warning was read as presence of a behaviour.* **Two checks I ran failed as instruments before one worked**, which is the transferable lesson. `CC_ENABLE_DEBUG_OUTPUT=1` through `xtask` returned zero hits for `fprofile-use` - but a positive control for flags that MUST be present (`TB_NO_HELPER_API`, `/TP`, `std:c++17`) also returned **zero**, proving the log never contained C flags and the null was empty. A `cargo build -vv` run then failed its positive control too, until `CC_ENABLE_DEBUG_OUTPUT=1` and `-vv` were combined, at which point the controls read 1, 4 and 2 and the invocation appeared. **Never accept a null from a log until a flag you know is present shows up in it.** Practical consequence of the finding: negligible and uniform. **Tablebases are unaffected and work normally** - this is about how `tbprobe.c` is compiled (`-O2`, no profile guidance), not about whether probing runs or is correct. The only party affected is a user who configures `SyzygyPath`, who gets correct probing that is marginally less optimised. It cannot have contaminated any measurement: `SyzygyPath` defaults to empty and `can_probe` returns false while `largest() == 0`, `sprt.ps1` and `gauntlet.ps1` never set it, and `datagen.ps1` passes `-tb`/`-tbpieces`/`-tbadjudicate` to **fastchess**, so even there the adjudicator's tablebase code is used and not Rarog's Fathom. **Not worth fixing:** MSVC PGO (`/GL` + `/LTCG:PGI`) cannot consume rustc's LLVM profile, so there is no shared-profile route on the primary platform. **Retry trigger:** revisit only if D.4 makes probe throughput matter, or if the C surface grows beyond one file. **Still open, by design not by omission:** Windows ARM64 has not rebuilt under `cc` 1.4.5; the A.9 release CI covers it, since RAR-P15 established that its bench cells run `verify-isa` on all five platform cells and check cross-platform determinism.
