# RAR-P51 — Two build choices read for speed on the match host: Rarog linked in MSYS2's clang64 environment against the MSVC build, and `--native` against the pext tier — REGISTERED 2026-10-30, before the read

Indexed under *6. Throughput, build and platforms* in [`docs/EXPERIMENTS.md`](../EXPERIMENTS.md).

- **Date / owner:** registered 2026-10-30 by the agent at the maintainer's
  request; the maintainer runs the reads (about 15 to 30 minutes).
- **Kind:** performance qualification of two build choices. The engine
  source is unchanged, and every build benches the development fingerprint.
- **Questions.**
  1. `clang64`: does Rarog built in MSYS2's clang64 environment, the one
     Basilisk builds in, run faster or slower than the MSVC build that every
     test binary uses now?
  2. `native`: is `--native` faster than the pext tier on this Zen 3 (Ryzen
     9 5950X)? The README says a native build is "usually a little faster",
     but this was never measured here. Basilisk measured the opposite on
     this host with the same LLVM major (BAS-P22, BAS-P26): Clang
     `-march=native` read −1.04% against its pext tier. All of that loss came
     from the `znver3` tuning model: native's instructions with
     `-mtune=generic` read −0.04%.
- **What clang64 can and cannot change for Rarog.** Basilisk is C++, so
  its environment picks the compiler of all its code; there Clang beat GCC by
  2.7% and MSVC by 14% (BAS-P22). Rarog's code is generated by rustc's own
  LLVM, in every environment. MSYS2 supplies the linker, the C runtime and
  the C compiler of Fathom, which `bench` does not reach. BAS-P22's compiler
  ranking therefore does not transfer.

## Arms

Three pools of four `cargo xtask build --arch pext --pgo` builds, by
`tools/nps_build_pool.ps1`.
- **Source:** `327f1e3`, clean. Its diff from `dd696ce` is
  `tools/nps_build_pool.ps1` alone, so the engine inputs are `dd696ce`'s.
- **Location:** `analysis/artifacts/toolchain-native-2026-10-30/`.
- **Manifests:** each pool's `manifest-pext.txt` holds its SHA-256s with
  the toolchain, triple, `rustc -vV` and linker environment.

| Pool | Recipe | First hashes |
|---|---|---|
| `pext` | the current recipe: `1.99.1-x86_64-pc-windows-msvc`, MSVC `link.exe`, VCRUNTIME140 and the UCRT | `F269844A`, `24979B8A`, `227E2032`, `99DB435C` |
| `native` | `pext` with `-Native` (`target-cpu=native`, `znver3` here) | `141D7D4D`, `18538ACD`, `0C043853`, `CC1C1E8D` |
| `clang64` | `pext` with `-Toolchain 1.99.1-x86_64-pc-windows-gnullvm -Target x86_64-pc-windows-gnullvm`; linker and C compiler `C:\msys64\clang64\bin\clang.exe` (MSYS2 Clang 23.1.4, LLD), archiver its `llvm-ar.exe`; the UCRT | `A5621812`, `17C54079`, `46D2E7A1`, `985371D4` |

- **One compiler.** All three are rustc 1.99.1 (`58cf8f9c3`) on LLVM 23.1.1,
  so the Rust code generation is the same compiler at the same flags.
- **What `clang64` changes:**
  - the linker and its layout (`.text` 949 KB against 763 KB: the
    gnullvm standard library brings more code);
  - `memcpy` and `memset` come from the UCRT instead of VCRUNTIME140;
  - stack probes and unwinding come from LLVM's runtime;
  - Fathom is compiled by Clang.
- **`clang64` runtime DLL.** The binaries import `libunwind.dll`, which
  MSYS2 keeps in `clang64\bin`. The engine is built `panic = "abort"`, so
  nothing per node unwinds; the DLL only has to load. A copy sits beside the
  builds (SHA-256 `a59c1ca4…`), and Windows loads it from the executable's
  directory first.
  - All four builds start and bench with only `System32` on PATH.
  - Without the copy they do not start.
- Every build of every pool benches 13,987,223.

## Exposure before registration

- Every build's `bench 13`, checked by the pool builder; `bench 1` of the
  `clang64` builds with a minimal PATH.
- **The instruction mix of `native` against `pext`** (`llvm-objdump`, all
  four builds of each pool; identical counts within a pool):
  - instructions in `native` and not in `pext`: `bextr` 81 sites,
    `vpmovsxbq` 26, `vpmovsxwd` 1, one SSE4a `insertq`, one `leave`;
  - in `pext` and not in `native`: `vblendpd` 1, `vpermd` 2;
  - `hlt`, `in` and `out` also appear: data decoded as code, a layout
    artefact.
  - So the native build uses no instruction family the pext tier lacks,
    apart from one `insertq`. It differs in which instructions the `znver3`
    model chooses: `bextr`, which is a single cycle on Zen, for shift and
    mask pairs. A read of `native` against `pext` is therefore a read of
    the tuning model, as in BAS-P26.
- The imports and section sizes of `clang64` against `pext`, as above.
- No NPS figure of any arm was read or computed.

## Instrument

`tools/nps_read.py`, PROCESS's two-step pooled read, in gain form with the
candidate over `pext`. Two reads, `clang64` first, each from an idle host.

## Prediction, frozen before the read

| Read | Prediction | 80% interval |
|---|---:|---|
| `clang64` over `pext` | 0.0% | [−1.0%, +1.0%] |
| `native` over `pext` | −0.8% | [−1.8%, +0.2%] |

- **`clang64`.** The compiler, flags, code and C runtime family are the
  same. What is left is layout, the routines `memcpy` and `memset` resolve
  to, and the linker. The per-node code calls no allocator and should call
  no `memcpy`. Layout alone moves a PGO build by about the pool-to-pool
  spread, so there is no lean.
- **`native`.** This is the LLVM major Basilisk read, on the same CPU, and
  the static check shows the same kind of difference: the tuning model's
  instruction choice. It cost Basilisk 1%. Rarog has been memory-latency
  bound since C.12, which should blunt a scheduling effect, so the lean is a
  little smaller.

## Decision and stop rule

- **`clang64` accepted:** the maintainer is offered the clang64 toolchain
  for local test and match binaries. The release toolchain is a separate
  decision, because the release builds on GitHub's Windows runners.
  **NO_CHANGE:** nothing changes, and MSVC stays.
- **`native` accepted:** the README's claim stands.
  **NO_CHANGE:** the README stops calling the native build the fastest
  one, and local pool and match binaries are built without `-Native`. If the
  estimate is −0.5% or lower, the README says plainly that the portable
  pext build is the faster one on Zen 3.
- **Steps:**
  - Step 1 first. Step 2 (`--extend`) runs only when step 1 says "between".
  - A disturbed step is repeated once into a fresh directory. A second
    disturbance stops for the maintainer.
- Nothing in the pools, instrument or thresholds changes after the first
  read starts.

## How to run

From PowerShell 7 on an idle host: no engine, harness or build, and no
other session's work. The two reads take about 15 minutes, plus 8 for each
step 2:

```powershell
cd D:\code\rarog; $A = "analysis\artifacts\toolchain-native-2026-10-30"; python tools\nps_read.py --base $A\pext --cand $A\clang64 --out $A\read-clang64 --label "RAR-P51 clang64 over MSVC"; python tools\nps_read.py --base $A\pext --cand $A\native --out $A\read-native --label "RAR-P51 native over pext"
```

Each read ends with a `verdict:` line. If one says "between", run its step
2, for example
`python tools\nps_read.py --extend analysis\artifacts\toolchain-native-2026-10-30\read-native`.
