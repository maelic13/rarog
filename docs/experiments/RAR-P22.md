## Part 1

**A.4.3 direct `pext` versus `base` NPS - REGISTERED 2026-09-10, prediction frozen while the run was in flight and before any result was seen.** RAR-P20 measured the ladder in two hops and its own calibration forbids chaining them: the same four `avx2` binaries read **+1.46%** apart between RUN2 and RUN3, so the compounded `base`-to-`pext` figure of about **+7.2%** (1.0459 x 1.0245) is an estimate that crosses a session drift. That figure is also the one that says what a user on the wrong asset actually loses, so A.4.4's README cannot quote it until it is measured directly. **Conditions:** idle 5950X, Windows x86-64, `rustc 1.98.1`. The pools are **reused from RAR-P20**, so both arms are built from `fc6e39d`, four builds per tier, all SHA-256-distinct and all at fingerprint 7,601,220 per `manifest-base.txt` and `manifest-pext.txt`. `tools/nps_multibuild.ps1 -Cycles 10 -Repeats 3`, `base` as the baseline arm, `pext` as the candidate, interleaved with alternating direction. **Provenance note, stated because the head has moved since those pools were built:** `1bf8171` (`cc` 1.4.5) and `e66bb51` (A.4.2 advisory) both landed afterwards, and both are behaviour-neutral with the fingerprint held, so the tier ratio measured here carries to the current head. The `cc` bump cannot affect it at all - it changes only `tbprobe.c`, which is unreachable without `SyzygyPath` set.

## Part 2

**Prediction, frozen 2026-09-10 before exposure:** **+6.0% to +8.5%**, point estimate **+7.2%**, the compounded value. Confidence high on the sign, moderate on the magnitude. The interval is deliberately wider than RAR-P20's individual CIs because the thing being tested is precisely whether compounding across a drifting session was legitimate.

## Part 3

**This row is a consistency check on RAR-P20 as much as a new number.** A result inside the band says the two hops were internally sound despite the drift, and A.4.4 may quote the direct figure. A result **outside +5.0% to +9.5%** says compounding was not legitimate, and the reading is not "the ladder changed" but "one of RAR-P20's runs carried something the interleaving did not absorb" - in which case RUN2 and RUN3 are re-examined before any README text is written, and the individual hops are re-measured rather than patched. **RESULT - RUN 2026-09-10: +6.65%, 95% CI [+6.48%, +6.89%], inside the frozen band.** Pooled median 2,963,438 -> 3,160,590 n/s; pooled best-of +7.40%; per-build medians 2.955-2.969 M against 3.153-3.167 M, with no overlap between the arms. Under the reading rule the first branch fires: the two RAR-P20 hops were internally sound, and A.4.4 may quote **+6.65%** as the measured cost of running `base` on a CPU that could run `pext`.

## Part 4

**Calibration, appended after exposure; the prediction is not rewritten.** Sign correct, and the result landed inside the frozen +6.0% to +8.5% band - but **below** the +7.2% point estimate, and that gap is the finding. **Chaining overstated the ladder by 0.50 percentage points, and the direct interval excludes the chained value**: compounding RAR-P20's hops gives 1.0459 x 1.0245 = **+7.15%**, which sits outside [+6.48%, +6.89%]. So the decision not to let A.4.4 quote the chained figure was correct on the merits, not merely cautious. **What was actually wrong is identifiable, and it is not the drift.** The suspicion on record was that the +1.46% session drift between RUN2 and RUN3 had contaminated the compounding. It had not - interleaving absorbed it, as designed. The culprit is **precision**: RUN2's interval was [+3.79%, +5.83%], **2.04 pp wide**, so its +4.59% point estimate carried about a percentage point of slack. Back out the direct result through the well-measured `pext`-over-`avx2` hop and `base`-to-`avx2` implies **+4.10%** - comfortably inside RUN2's own CI, so nothing contradicts anything. The chained number was not wrong so much as it inherited RUN2's imprecision and then multiplied it. **The direct run is 5x tighter at 0.41 pp**, which is what a single interleaved comparison buys over two composed ones. **Transferable rule: compose ratios only when each is tighter than the difference you care about.** Two hops at +-1 pp cannot answer a question to +-0.5 pp, however carefully each hop was run. **Drift continued and remained harmless:** `base` read 2,922-2,934k in RUN1, 2,940-2,961k in RUN2 and 2,955-2,969k here, an upward march across the session consistent with thermal settling, and absorbed within each run exactly as the alternating-direction design intends. **Speed is not Elo.** At RAR-M20's ~2 Elo per 1% this is roughly **13 Elo** between the extreme assets - a real number for a user who picks wrong, and still a conversion for reasoning about candidates rather than a gate result. **RAR-P20 is not superseded**: its two hops stand as measured, and this row refines the composite they could not deliver. **Speed is not Elo.** At RAR-M20's ~2 Elo per 1% the result would imply roughly 12 to 17 Elo between the extreme assets, and that conversion is for reasoning about candidates, never a gate. **No decision rule is attached because none is owed:** this measurement selects nothing and accepts nothing. It exists so that a number the README will print to users is measured rather than inferred. **Retry trigger:** re-run when the tier set changes, when NNUE lands in Phase F, or on a pinned-compiler bump.
