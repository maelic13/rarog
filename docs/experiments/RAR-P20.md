# RAR-P20 — A.4.1 per-tier NPS: what does the ISA tier actually buy? REGISTERED 2026-09-10, NOT YET RUN

Indexed under *6. Throughput, build and platforms* in [`docs/EXPERIMENTS.md`](../EXPERIMENTS.md).

## Experiment and conditions

**A.4.1 per-tier NPS: what does the ISA tier actually buy? REGISTERED 2026-09-10, NOT YET RUN.** The A.4 design choice between a fat binary (option a) and multiversioning only the PEXT kernels (option b) turns on one number the ledger does not contain: what **global** `x86-64-v3` codegen is worth outside the slider kernels. Option (b) keeps one ~800 KB binary but compiles everything except the multiversioned kernels at baseline; if that costs nothing, (a) buys ~2.4x binary size for nothing, and if it costs several percent, (b) is not viable. A second question rides along: whether the `pext` tier earns its place over `avx2` at all. **Conditions:** idle 5950X (maintainer confirmed idle 2026-09-10), Windows x86-64, `rustc 1.98.1`, source `ef9c6ae`, clean tree. **Four independent PGO builds per tier** via `tools/nps_build_pool.ps1`, which refuses the pool unless every copy is SHA-256-distinct (identical bytes mean the profile did not vary and pooling measures nothing) and every copy reproduces bench fingerprint **7,601,220** before entering the pool. Measured with the existing `tools/nps_multibuild.ps1 -Cycles 10 -Repeats 3`, which interleaves one reading of every build per cycle, alternates direction, and reports a pooled-median delta with a 2,000-sample bootstrap CI. **Three runs, in this order:** (1) **NULL**, `base{1,2}` against `base{3,4}` - same source, same tier, different profile luck; (2) **avx2 against base** - the deciding number, no source difference, codegen only; (3) **pext against avx2** - the `rarog_pext` source path in `attacks.rs`.

## Result / disposition

**Prediction, frozen 2026-09-10 before any run.** NULL: straddles zero, absolute pooled median **under 1%**. avx2 vs base: **+2% to +6%** - Rarog is a bitboard engine and `x86-64-v3` brings BMI1 (`andn`, `blsr`, `tzcnt`) and LZCNT into every move loop, not only the sliders. pext vs avx2: **+2% to +7%** on fast-PEXT hardware. Confidence moderate on the signs, low on the magnitudes; the honest state is that neither has ever been measured in this engine. **PROSPECTIVE DECISION RULE, fixed now so it cannot be invented after exposure.** (i) If the NULL fails to straddle zero or its absolute median reaches 1%, the instrument is not calibrated at this resolution and **runs 2 and 3 are not read at all** - the tier question stays open and the pool size goes up. (ii) If run 2's CI **upper** bound is below **+1.5%**, global v3 codegen is worth under about 3 Elo, option (b) becomes the preferred design and A.4.2 is re-scoped to multiversioning. (iii) If run 2's CI **lower** bound is above **+1.5%**, option (a) is confirmed and A.4.2 proceeds as the fat binary. (iv) If the CI spans +1.5%, the run is **inconclusive**: default to (a), record it as unresolved rather than as support. (v) If run 3's CI straddles zero, the `pext` tier does not pay for itself and the universal binary ships **two** tiers, not three. The **1.5%** threshold is not free-chosen: RAR-M20 records the ~2 Elo per 1% NPS constant at STC, so 1.5% is about 3 Elo, the smallest tier difference worth carrying a second code path for. **RESULT - RUN 2026-09-10, all three runs complete; option (a) confirmed and all three tiers earn their place.** Source `fc6e39d`, engine-identical to `ef9c6ae` (only `EXPERIMENTS.md`, `GUIDE.md`, `PLAN.md` and `tools/nps_build_pool.ps1` differ, zero paths under `src`, `xtask`, `build.rs` or `Cargo.*`); twelve builds, all SHA-256-distinct, all at fingerprint 7,601,220. **RUN1 NULL** `base{1,2}` against `base{3,4}`: **-0.15%**, 95% CI **[-1.26%, +0.66%]** - straddles zero with an absolute median under 1%, so clause (i) passes and runs 2 and 3 are readable. **RUN2 avx2 against base**: **+4.59%**, CI **[+3.79%, +5.83%]**, per-build medians 2.94-2.96 M against 3.08-3.09 M with every candidate build above every baseline build. **RUN3 pext against avx2**: **+2.45%**, CI **[+2.32%, +2.62%]**, again with no overlap between the two arms' per-build medians. **Verdict under the frozen rule:** clause (iii) fires - RUN2's lower bound of +3.79% is two and a half times the +1.5% threshold - so **option (a), the fat binary, is confirmed and option (b) is rejected**, because multiversioning only the slider kernels would forfeit the 4.6% that global `x86-64-v3` codegen delivers everywhere else in the engine. Clause (v) does not fire: RUN3's interval excludes zero by a wide margin, so a universal binary carries **three** tiers, not two.

## Conditional lesson and retry trigger

**Calibration, appended after exposure; the prediction above is not rewritten.** Both signs and both magnitudes landed inside the frozen bands - avx2 against base predicted +2% to +6% and measured **+4.59%**; pext against avx2 predicted +2% to +7% and measured **+2.45%**. The one soft miss is **magnitude on RUN3**: the result sits at the very bottom of a band whose width admitted +7%, so that band was too generous rather than wrong, and a future prediction about swapping a single source path should be narrower. **A CONFOUND worth more than the calibration: the host drifted upward across the session, and the same binaries prove it.** The four `avx2` builds pooled to **3,087,416** n/s as the candidate arm in RUN2 and to **3,132,586** n/s as the baseline arm in RUN3 minutes later - **+1.46% for identical bytes**. `base` moved the same way, 2,929,182 in RUN1 to 2,951,930 in RUN2, **+0.78%**. The likeliest cause is thermal and boost settling after the twelve-build burst that immediately preceded RUN1. **This touches none of the three verdicts**, because `nps_multibuild.ps1` interleaves both arms within a run and alternates direction, so a slow drift loads both arms equally - that is what the design is for. What it forbids is **chaining runs**: the tempting base-to-pext figure of about **+7.2%** (4.59% compounded with 2.45%) spans the drift and is an **estimate, not a measurement**. That is also the number that says what a user on the wrong asset actually loses, so if it is going to be quoted it needs its own direct `pext` against `base` run, about ten minutes. **Appended 2026-09-10: that run is RAR-P22, and it measured +6.65% [+6.48%, +6.89%], so the ~7.2% chained figure above is superseded for quotation - the direct interval excludes it. The cause was RUN2's 2.04 pp width, not the drift.** **Speed is still not Elo.** At RAR-M20's ~2 Elo per 1% constant the ladder is worth roughly 9 Elo from base to avx2 and about 5 more to pext, but that constant is for reasoning about candidates and no gate has measured it in this engine. **Retry trigger** unchanged: a change to the tier set, NNUE landing in Phase F (which is what would make AVX-512 tiers worth revisiting), or a pinned-compiler bump. **Leaf identifiers:** the prototype leaf named in clauses (ii) and (iii) was renumbered A.4.2 to A.4.3 on 2026-09-10 when the `cc`/Fathom leaf was inserted ahead of it; bounds, thresholds and rule text are unchanged. **Read this row for what it is: a zero-game speed measurement, and speed is not Elo.** RAR-M20's constant is a conversion for reasoning about candidates, never a substitute for a gate. **Cost is about 40 minutes** - twelve PGO builds at roughly 45 s, then three pooled runs of about 10 minutes. Maintainer-run because it occupies the box; `nps_build_pool.ps1`'s guards were verified live before handoff, including a deliberately absurd `-ExpectFingerprint` that correctly aborted the pool. **Retry trigger:** re-run when the tier set changes, when NNUE lands in Phase F (which is what makes wider AVX-512 tiers worth revisiting - 79% of Stockfish's ISA-specific code is NNUE inference, and we have none), or on a pinned-compiler bump that changes codegen.
