# B.3.3 curvature sweep, 2026-09-24

PLAN B.3.3; ledger RAR-S79 (the cluster) and RAR-S80 (the categoricals whose
one adoption the arm now carries). Zero games. This file answers one question
for PLAN rule 4: do the proof cluster's main coordinates show curvature at
fixed nodes, which an SPSA needs in order to have something to find? The
classification rule in section 2 was written and committed before any sweep
point was measured (`e72b86f`).

**Result:**
- The bake (`3ca9aab`) reproduces the measured arm exactly: new arm
  **7,978,292 / EBF 2.465**, off arm unchanged at 7,185,678 / 2.444
  (section 3).
- **Three of seven coordinates curve:** `CoreNmpREval`, `CoreProbcutBase`
  and `CoreSingularMargin`. `CoreNmpBase`, `CoreSingDoubleBase` and
  `CoreSingTripleBase` are monotone; `CoreLmrSingularOffset` is flat
  (section 4).
- The SPSA configuration was not written. The instruction's 35-coordinate
  surface is 36 once amendment 5 is counted, and it waits on RAR-S78's bake
  (section 6).

## 2. Classification rule (frozen before any measurement)

**Coordinates and points.** Seven coordinates, each at 0.5×, 0.75×, 1×, 1.5×
and 2× its default, rounded half away from zero, clamped to the declared
range (no point needs the clamp). `CoreSingDoubleBase` has default 0, so its
points are fixed instead at −40, −20, 0, 40, 80.

| Coordinate | Default | Range | 0.5× | 0.75× | 1× | 1.5× | 2× |
|---|---:|---|---:|---:|---:|---:|---:|
| `CoreNmpBase` | 150 | 0..=400 | 75 | 113 | 150 | 225 | 300 |
| `CoreNmpREval` | 1044 | 0..=3072 | 522 | 783 | 1044 | 1566 | 2088 |
| `CoreProbcutBase` | 180 | 50..=400 | 90 | 135 | 180 | 270 | 360 |
| `CoreSingularMargin` | 4 | 1..=12 | 2 | 3 | 4 | 6 | 8 |
| `CoreLmrSingularOffset` | 85 | 0..=300 | 43 | 64 | 85 | 128 | 170 |
| `CoreSingDoubleBase` | 0 | −100..=200 | −40 | −20 | 0 | 40 | 80 |
| `CoreSingTripleBase` | 16 | 0..=80 | 8 | 12 | 16 | 24 | 32 |

The first five are PLAN's sweep coordinates; the double and triple bases
were added by amendments 5 and 6 of `analysis/b3_research_2026-09-23.md`.
One coordinate moves at a time; the others stay at their defaults. The 1×
point is one run shared by all seven.

**Measurements per point**, run one at a time on an idle host:
- `bench 13` nodes. The engine gets `setoption` and then `bench 13` under
  the watchdog driver, and the total comes from the driver's log.
- WAC solved at 100,000 nodes: `tools/diag/fixed_budget_probe.py nodes
  100000 src/wac.epd` with the option in the engine spec. The probe stops
  on an option the engine does not report, and a bench log that contains
  `No such option` is a failed run, not a point.

Every number in the tables comes from a script over these outputs.

**Rule.** For each coordinate:
- The *best point* is the one with the most WAC solved, ties broken by fewer
  bench nodes.
- The best point *beats an end* when it solves at least 2 more WAC positions
  than that end. It also beats the end when its bench nodes are at least 3%
  fewer (`N_best ≤ 0.97 × N_end`) and it solves no fewer WAC positions.
- **Curved:** the best point is interior (0.75×, 1× or 1.5×) and beats
  both ends.
- **Monotone:** not curved, and the better end (by the same ordering) beats
  the other end.
- **Flat:** neither.

**What it does not decide.** Fixed-node WAC and bench nodes are not Elo.
RAR-S80 has just shown that a −11.5% bench and +10 WAC switch reads +3.1 ± 9.1
in games. A curved coordinate shows only that the surface has an interior
the SPSA could find. It does not show that the SPSA will gain. The SPSA
surface is registered separately (RAR-S81, not yet written). PLAN rule 4
reads this table as activation and curvature evidence.

## 3. The bake (part 1, `3ca9aab`)

RAR-S80 set the shared `SingularTtDepthMargin` to 2 on the arm's tune build.
On that build the head's consumer (`core/node.rs`, the `allows_singular`
call) and the legacy node are compiled out, so the option moved only the
`b3proof` candidate gate. That gate now reads a proof-owned coordinate:
`ProofParams::singular_tt_depth_margin`, UCI `CoreSingularTtDepthMargin`,
default 2, range 0..=4. The shared option, its default 3, its tripwire
assert and the head's and legacy consumers are unchanged.

| Check (`bench 13`, all 40 lines compared) | Result |
|---|---|
| off arm, default features | **7,185,678 / EBF 2.444**, 40/40 lines equal to B.3.1's record |
| new arm, `--features b3proof` | **7,978,292 / EBF 2.465** |
| new arm tune build (`b3proof,tune`) at its defaults | 7,978,292 / 2.465, 40/40 equal to the arm |
| old arm tune build (RAR-S80's, sha256 `F49E78C9…6D07`) at its defaults | 7,479,114 / 2.467 |
| old arm tune build with `SingularTtDepthMargin=2` (what RAR-S80 measured) | **7,978,292 / 2.465, 40/40 equal to the new arm** |
| new tune build with `CoreSingularTtDepthMargin=3` (the coordinate is live) | 7,479,114, 40/40 equal to the old arm |
| new tune build with `SingularTtDepthMargin=3` (the shared option no longer reaches the arm) | 7,978,292, unchanged |

The bake reproduces what was measured: the new arm at its defaults equals the old
arm with the option, and the new coordinate at 3 gives back the old arm.
The arm searches 6.7% more nodes than before, the same +6.67% that B.3.2's
categorical screen recorded for this switch.

## 5. Reads beside the rule (not part of the classification)

- **The default is a bench-node peak on every axis.** 24 of the 28 perturbed
  points search fewer `bench 13` nodes than the default. This is not an
  instrument effect: each coordinate set to its own default by `setoption`
  reproduces 7,978,292 exactly (`controls/`). Nor is it one position. Against the per-position
  median of the 28 points, positions 38, 4, 39, 5 and 16 carry +0.96M of
  the default's +1.46M excess, and on each of them 25 to 28 of the 28 points
  are below the default (`default_outlier.txt`). The baked margin raised the
  arm by 6.7%, and almost any single-coordinate move takes it back down.
  None of the curved labels depends on this, since all three rest on WAC.
- **The fixed-node WAC surface is rough.** Adjacent points differ by up to
  13 solved (`CoreProbcutBase` 90 → 135). On six of the seven axes at least
  one point solves more than the default's 233; on `CoreNmpBase` none does.
  The runs are deterministic, but a one-step change reorders the tree, and
  the rule carries no noise estimate. "Curved" here means an interior WAC
  maximum at this resolution, not a smooth optimum an SPSA would find
  easily.
- **Consistency with B.3.2.** The default point, 233 WAC and +6.7% nodes on
  the previous arm, matches B.3.2's `SingularTtDepthMargin=2` categorical
  screen (233, +6.67%), which was measured on a different build (diag+tune)
  of the same source.
- **The largest mover is `CoreSingularMargin`:** 6 gives +12 WAC and −30.5%
  nodes, and 8 gives +4 and −39.2%. At fixed nodes the arm prefers fewer
  singular candidates than its seed allows. RAR-S80 showed with
  `CoreSingularFloor=1` (+10 WAC and −11.5% nodes at fixed nodes, +3.1 ± 9.1
  Elo in games) that such a read is not Elo.
- **The first sweep attempt was discarded.** Python on Windows wrote the
  points file with CRLF, so each option carried a trailing carriage return.
  The attempt was stopped after two points, its outputs deleted, and all 29
  points were re-run with the file stripped and checked. The one point
  measured in both runs read the same bench (6,779,485).

## 6. The SPSA surface: not prepared, because a premise is false

The instruction was to prepare `config_b33.json` and `fixed_b33.json` for
"the 35-coordinate surface listed in the packet". The packet's list
(*SPSA surface*, written with the contract) does count 35. Amendment 5 then
made the double bar's base a coordinate "for the sweep and the SPSA"
(`CoreSingDoubleBase`), and amendment 6 repeats that the sweep and the SPSA
decide both bars. The packet as amended therefore lists **36**:

| Group | Count |
|---|---:|
| NMP margin | 5 |
| NMP reduction | 5 |
| NMP verify depth | 1 |
| ProbCut | 6 |
| singular margin | 1 |
| double bar, base included | 5 |
| triple bar | 5 |
| multi-cut lerp | 1 |
| LDSE | 1 |
| LMR term | 3 |
| LMR bases | 3 |
| **Total** | **36** |

Which of these the tune should use is a registration decision, so no
configuration was written. There are two readings:
- **36, as amended** (recommended). Amendment 5 names the SPSA explicitly,
  and this sweep classifies `CoreSingDoubleBase` monotone: it has a
  gradient at fixed nodes, toward a stricter bar.
- **35**, with `CoreSingDoubleBase` fixed at 0 in `fixed_b33.json`. This
  contradicts amendment 5.

Once the count is decided, the configurations follow these rules:
- `value` is the engine default and `min_value`/`max_value` the declared
  range.
- `step = max(2, round((max − min)/16))`, half away from zero. This is the
  README's class rule, and it keeps every coordinate above audit class 6 at
  N = 5,000.
- The Colosseum files come from `spsa_config_to_colosseum.py b33 --iterations 5000`
  (`c_end = step · N^−0.102`, as RAR-S78; the horizon itself is RAR-S81's
  to fix), with `r_end` 0.0031.
- `fixed_b33.json` holds Hash 64, Threads 1 and MultiPV 1; the five core
  switches and the four proof switches at their defaults;
  `CoreSingularTtDepthMargin=2`, a game-decided value; and every other
  `Core*` spin at its default.
- `CoreProbcutTtMargin` is excluded, because its switch is off.

**Dependency on RAR-S78.** B.2.7's re-tune (`b27all`) is still running and
covers all 82 `CoreParams` coordinates, not only the three LMR bases. The
arm inherits those parameters, so baking RAR-S78's theta changes three things:
- the seeds of `CoreLmrQuiet`, `CoreLmrNoisy` and `CoreLmrCutNode` in
  `config_b33`;
- every fixed `Core*` value in `fixed_b33`;
- the arm's fingerprint, which moves again.

Configurations written before that bake would fail the audit's seed check
(class 3) once it lands. RAR-S81 is not registered and no horizon is
proposed.
