# Move generation optimization — RAR-M31 / 4.11b.8

## Decision

**Disposition, 2026-09-07: reject the candidate for now and restore the previous
x-ray calculation; retain the independent pin oracle.** The original retention
decision for `2ea279f` versus `407de51` is SUPERSEDED. Isolated-generator gains
remain valid historical observations; neither whole-search interval establishes
a gain. This is insufficient evidence of useful deployed value, not proof of
zero benefit, a slowdown, or a correctness defect.

The later `b592b40` research contract asks for a prospective practical
whole-search floor, which the original run never registered. No new floor is
applied to those exposed observations. Instead, stop investment in this bounded
candidate and withdraw it from dev. Another standalone timing campaign is not
the next priority: local gains are already established, the remaining question
is small whole-search value, and upcoming 4.11b.10 changes the pin producer's
lifetime/consumers. A campaign now could qualify an implementation soon replaced.
This prioritization is a research judgment, not a statistical rejection test.

The restoration starts from `b90232b`, retaining subsequent LazyMargin/cache/
search fixes. It changes neither the board representation nor NNUE enablement.
No performance or Elo benefit is claimed for the restoration. Keep RAR-M31's
recipe so 4.11b.10 can reconsider the algorithm if its remaining measured cost
justifies it. Before any retry, freeze the current baseline, exact consumer
scope, production build settings, practical whole-search floor, uncertainty
rule and fixed run budget. Do not bank its old microbenchmark gain again as a
new result. Playing qualification for the broader cluster remains 4.11b.17.

The baseline (now restored) performs four occupied-board slider lookups to see
through friendly pieces. The withdrawn candidate finds aligned enemy sliders
with two empty-board lookups, intersects BETWEEN with **all** occupancy, and
retains a sole friendly blocker. Zero blockers add nothing; two blockers or
a sole enemy blocker cannot pin. No persistent state or NNUE interface changes.
The existing generators receive the same pin bitmask, so their traversal,
capture/quiet partition, promotions and output order are unchanged.

Reckless's `src/board.rs` pin/check update also scans candidate sliders and
intervening blockers, but uses enemy occupancy in its initial attack queries
and maintains state for both colors. Rarog does not import that state lifetime
or its broader threat maintenance. That remains a separate architecture choice.

## Other inspected opportunities

Rarog already uses compile-time capture/quiet modes, setwise unpinned pawn
generation and MaybeUninit move lists. Color specialization and broad king-target
rewrites were not added to this bounded candidate.

`cargo rustc --release --lib --no-default-features -- --emit=asm` showed a
520-byte memcpy in `generate_captures_pinned`. Constructing and filling the
return tuple directly still emitted that copy, so the trial was dropped.
These are library assembly observations, not proof of the final LTO caller's
cost. A larger delivery change belongs with 4.11b.14's representation decision
and must inspect the actual production caller before claiming a copy saving.

## Measurement

Windows x86-64, rustc 1.97.1 / LLVM 22.1.6. Both arms use identical build
settings within each comparison, no Cargo features, no PGO and no diagnostic
instrumentation. Generic uses default x86-64/magic; PEXT uses the xtask flags
`--cfg rarog_pext -C target-cpu=x86-64-v3 -C target-feature=+bmi2`.

Three alternating rounds of the existing board-v2 executable, each with its
own warm-up and seven 25-ms samples, give these medians of round medians:

| Isolated operation | Baseline M operations/s | Candidate M operations/s | Change |
|---|---:|---:|---:|
| Legal generation | 256.409 | 278.307 | +8.54% |
| Capture generation | 75.422 | 84.044 | +11.43% |
| Staged generation | 208.632 | 224.086 | +7.41% |
| Make/unmake | 48.032 | 48.240 | +0.43% |
| Threshold SEE | 87.727 | 87.113 | −0.70% |

Every candidate generation round beat every baseline round for its operation.
The unchanged operations are timing controls, not evidence of changes to them.

Full-search confirmation uses `board_search_profile_v1.epd`: 20 roots, Hash
16 MiB, one thread, 600,000-node **limit** (not an exact completed-node count),
TT reset between roots. Each backend has one excluded warm-up per arm and
12 pairs, alternating which arm runs first. NPS is total reported nodes divided
by total reported search milliseconds; startup/reset time is excluded.

| Backend | Baseline median NPS | Candidate median NPS | Change | 95% bootstrap interval | Faster pairs |
|---|---:|---:|---:|---:|---:|
| Generic/magic | 3,381,312 | 3,400,469 | +0.57% | −0.51% to +1.00% | 7/12 |
| PEXT | 3,389,736 | 3,438,882 | +1.45% | −1.57% to +4.26% | 8/12 |

The intervals use 5,000 independent arm resamples, seed 4118. Neither excludes
zero; neither is an Elo estimate. Maximum total host busy time per search
batch was 6.41% generic and 12.25% PEXT, including the engine. The PEXT run
experienced greater background-load variation. All registered pairs are
retained; there was no result-based trimming or extension.

An earlier eight-pair generic screen measured +0.82%. Its one-round board
screen also moved unchanged make/unmake by +5.5%, so it was explicitly treated
as noisy screening, not the final local-performance estimate. The confirmation
above uses the final source and frozen builds. No NPS gain is claimed as proven.

- Full debug suite: 271 passed; release: 272 passed; zero failed or ignored.
- New independent mailbox ray walker checks both colors over seeded walks
  from every board-v2 root, requiring at least 1,000 checked king positions.
  It uses neither slider tables nor BETWEEN/LINE. Existing external legal,

  suppression or correctness relaxation was introduced.
- PEXT: the pin oracle plus 50 board-v2/board-correctness tests passed.
- All four immutable engine copies reproduce **7,601,220 / EBF 2.474**.
- 480 paired root comparisons across both backends match depth, seldepth,
  nodes, score type/value, full PV and best/ponder moves. The reproduction

  the original harness checked them.
