# B.5.2 — Tablebase root, in-search probes and PV: how should Rarog match Stockfish?

Opened 2026-09-27 as the starting record for PLAN B.5.2 (`RESEARCH`, `R2`). It
holds the report that raised the issue, what was verified in Rarog the same
day, and how Stockfish solves it, read from official master `0a215d6c`
(2026-09-22) in `D:/code/stockfish`. The investigation fills in the sections
marked *open* and ends `READY_FOR_IMPLEMENTATION` or `NO_CHANGE` per item.
Stockfish is described here, never copied (PROCESS, *The independence
boundary*).

## Decision needed

Which parts of Stockfish's tablebase-root handling Rarog adopts, with what
exact semantics, and how the implementation is verified. The maintainer's
intent (2026-09-27) is to solve it the way Stockfish does; the investigation
turns that into a checked implementation handoff and flags any part where the
Stockfish way conflicts with a Rarog contract.

## Known evidence

### The report (received 2026-09-27, summarised)

From the Basilisk 1.10.1 work (BAS-C13): at a tablebase root Rarog prints a
one-move PV and usually sends `bestmove` without a ponder move. Stockfish
extends decisive tablebase lines to mate (`syzygy_extend_pv`) and takes the
ponder move from that line; Basilisk now does the same. Reproduction, with
`SyzygyPath` set to `D:/chess/tablebases/syzygy3456`:

- `7r/5R2/8/2k1PB2/8/4K3/8/8 w - - 0 86`
- `8/P4k2/8/1N6/1P2B1K1/8/8/8 w - - 7 81`
- `1r6/R7/6k1/8/8/5PP1/6K1/8 w - - 6 72`

The report proposes the two-step extension (walk the searched PV while each
move keeps the best rank; then extend to mate by DTZ, ties broken by the
opponent's mobility), Stockfish's DTZ ranking for step 2, a Move Overhead time
box under a clock, extension of every line without a clock, and four tests on
a KQvK fixture. It warns that Fathom's `tb_probe_root_dtz` ranks every clean
win equally (rank 1000), so step 2 cannot use it, and claims the vendored
Fathom's DTZ probing is thread-safe despite the header's note. The report was
treated as a lead, not as authority; each claim is checked below.

### Verified in Rarog, 2026-09-27

Binary: `dev` at `e84e770`, default build (`2.5.0-dev+b3proof`, bench
12,897,901). All three positions, at `go depth 14` and at
`go wtime 60000 btime 60000 winc 600 binc 600`, alike:

| Position | Last info line | `bestmove` |
|---|---|---|
| `7r/5R2/8/2k1PB2/8/4K3/8/8 w` | `score cp 31743`, PV of 1 move | `e5e6`, no ponder move |
| `8/P4k2/8/1N6/1P2B1K1/8/8/8 w` | `score cp 31743`, PV of 1 move | `a7a8q`, no ponder move |
| `1r6/R7/6k1/8/8/5PP1/6K1/8 w` | `score cp 31743`, PV of 1 move | `f3f4`, no ponder move |

Mechanism, from the source (inference from reading; the investigation
confirms it by instrumentation):

1. `syzygy_root_moves` (`src/search/mod.rs:650`) ranks root moves with
   Fathom's `root_probe_dtz` and, when DTZ is available and the DTZ-preferred
   move (`tb_probe_root`) has the best rank, cuts the root to that single move
   (`mod.rs:680`).
2. `syzygy_wdl_score` (`mod.rs:1373`, called from `core/node.rs:618`) probes
   WDL at every non-root node inside the probe limits and returns the result
   at once, storing it in the TT as `Bound::Exact` with no move. Every child
   of a tablebase root is itself in the tablebase, so the PV ends at the root
   move, and `ponder_from_tt` (`mod.rs:1626`) finds no move in the child's
   entry.
3. The internal tablebase-win value (`TB_WIN_SCORE − ply`,
   `TB_WIN_SCORE = MATE_SCORE − 2·MAX_PLY`) reaches the GUI unmapped as
   `cp 31743`, which reads as a +317-pawn evaluation.

Other facts that constrain the design:

- `Move Overhead` defaults to 10 ms (`src/search_options.rs:52`).
- The search keys pruning and storage off `TB_WIN_SCORE`: `is_win`/`is_loss`
  (`core/node.rs:16–27`), ProbCut's return clamp, null-move and futility
  guards, the correction-history training gate (`core/node.rs:542`). A change
  of the displayed score must therefore be a UCI output mapping, not a change
  of internal values.
- Fathom's `tb_probe_root_impl` (bound in `src/syzygy.rs:47`) fills one result
  per legal move with its WDL and absolute DTZ, computed the same way as
  `root_probe_dtz`'s per-move value (vendored `tbprobe.c:2560–2600`), so a
  DTZ-ordered rank can be computed in Rust. It does not treat a move into a
  repetition or a rule-50 draw as a draw; Rarog's board can.
- Fathom's `root_probe_dtz` (`tbprobe.c:2342`) ranks clean wins at 1000,
  cursed wins at `1000 − (dtz + cnt50)`, losses mirrored: Stockfish's formula
  with DTZ ranking off. The report's pitfall is real for any use that needs
  DTZ order.
- The vendored header marks `tb_probe_root` "NOT thread safe"
  (`tbprobe.h:271`); the source has init locks (`tbprobe.c:79–106`). Whether
  a root DTZ probe may run while helper threads probe WDL is not established.
- The tests that need tables read `RAROG_SYZYGY_PATH` and skip without it
  (`tests/multipv_syzygy.rs`); CI has no tables.
- No Colosseum run file sets `SyzygyPath` (`tools/colosseum/*.toml`), so no
  gate, match or tune so far has probed a tablebase.

### How Stockfish solves it (`0a215d6c`)

1. **Root ranking** (`src/syzygy/tbprobe.cpp`, `root_probe` from line 1790,
   `rank_root_moves` from 1904). Every root move gets a DTZ-based rank. A move
   into a rule-50 draw or a repetition counts as DTZ 0. Clean wins rank
   equally unless DTZ ranking is requested; DTZ ranking is forced when DTZ
   equals distance to mate (pawnless, and three men or four with minors only,
   `Position::dtz_is_dtm`). A repetition already in the game drops wins to
   the DTZ-ordered band. If DTZ fails, WDL ranks the moves. The per-move
   display score: a clean win the mate-band value, a cursed win 1 to 49 cp by
   distance to the rule-50 border, a draw 0, losses mirrored.
2. **Root move set** (`thread.cpp:320`, `search.cpp:365–372`). Root moves are
   sorted by rank, none removed; the MultiPV loop searches each line within
   the group of equal rank, so the first line chooses among all best-ranked
   moves by search score.
3. **In-search probing** (`search.cpp:940–985`, `tbprobe.cpp:1951–1955`).
   Switched off for the whole search when the root is in the tablebase and
   DTZ is available, or when the root is not winning. Elsewhere a probe runs
   only after a zeroing move (rule-50 counter 0) within the probe depth and
   piece limit; a win is a lower bound and a loss an upper bound, the node
   returns only on a cutoff (stored in the TT at depth + 6, no move) and at a
   PV node otherwise continues with the bound applied.
4. **Displayed score** (`score.cpp:25–45`, `uci.cpp:564`). Tablebase values
   occupy their own band below mate scores and print as `cp ±20000 ∓ plies`;
   at a tablebase root the per-move display score replaces the search score
   unless the search found a mate.
5. **PV extension** (`search.cpp:2159–2294`, called from `output_pv` at 2327).
   For a decisive score that is not a mate: step 1 keeps the searched PV while
   every move keeps the best non-DTZ-ordered rank and no repetition or rule-50
   draw appears, and cuts it at the first failure; step 2 extends to mate
   with DTZ-ordered ranks, breaking ties by the opponent's replies after the
   move (−1 each, −100 per capture), and stops at mate, at a draw, or when
   DTZ is missing. A draw found on the way sets the displayed score to 0.
6. **Time box** (`search.cpp:2172–2178`). Only under time management: the
   extension stops once `2 · MultiPV · elapsed ≥ Move Overhead`, per printed
   line (Stockfish prints a line at every iteration), and then prints
   `info string Syzygy based PV extension requires more time, increase Move
   Overhead as needed.` Without time management it runs unbounded.
7. **Ponder move** (`search.cpp:254–266`). `pv[1]` of the printed, possibly
   extended line; the TT fallback only when the PV has one move.

## Unknowns (open)

- Whether the single-move root cut and the always-returning in-search probe
  are the whole cause of the one-move PV (instrumented fixed-depth runs).
- Rarog's semantics for each Stockfish part, one by one, and where a Rarog
  contract differs: TT bound handling for tablebase values, mate-distance
  scores against the tablebase band, the draw-score conventions, the
  B.2.0.2 MultiPV contract, the probe-depth and probe-limit options.
- Fathom thread safety for root DTZ probes during a parallel search; if not
  established, where the extension may run.
- The cost of the extension under a clock at the 10 ms default Move Overhead,
  and whether it can ever reach a forfeit.
- A test fixture that runs in CI (small pawnless tables such as KQvK and KRvK,
  their size and licence) or a documented local-only test.

## Hypotheses (open)

H1: the one-move PV and the missing ponder move come only from mechanisms 1
and 2 above; adopting Stockfish's root set and probe switch gives a full
searched PV and a ponder move before any extension. Competitor: the
extension is required even then, because the search's PV at a tablebase root
is short for another reason (e.g. mate-distance pruning in the tablebase
band). The investigation's instrumented runs separate the two.

## Interaction map (open)

At least: root move list and root probing (B.5's cluster code) -> root search
and MultiPV lines; in-search probe -> TT entries (bound, move, depth) -> TT
cutoffs, the ponder fallback and PV; tablebase score band -> pruning guards and
correction training (`TB_WIN_SCORE` consumers above) -> UCI output mapping; PV
-> ponder move -> B.3.5's ponder contract (one `bestmove` per `go`).

## Strength scope

Nothing here can move a result measured so far: no harness run file sets
`SyzygyPath`. With tablebases configured, the root changes only choose among
moves that keep the result, and the in-search probe semantics (bounds,
return on cutoff, zeroing-move condition) may change search from larger
positions by a small amount of unknown sign. The maintainer will design a
tablebase-enabled gate for the implementation when it is ready (decision of
2026-09-27); the investigation proposes what that gate must see.
